# Spec-driven разработка с кодинговыми LLM

## Размер процесса

Проект небольшой: достаточно Markdown, Git и проверок. Отдельный сервер спецификаций, генератор задач и длинные формальности не нужны. Для механики или изменения архитектурного контракта нужна отдельная spec; для небольшого дефекта достаточно REQ, сценария воспроизведения, плана и update. Документирование не должно становиться самостоятельным игровым фреймворком.

## Цикл задачи

1. **Контекст.** Прочитать AGENTS, документы по роли и соответствующие исходники. Проверить git status. Определить текущее поведение и расхождения.
2. **Spec.** Зафиксировать проблему, scope/non-goals, REQ, наблюдаемый результат, границы и неопределённые решения. Статус `draft`; ничего не выдавать за реализованное.
3. **Принятие.** Явная задача владельца может сразу принять ограниченную spec. Дополнительное подтверждение нужно для существенного невыбранного правила мира, а не для каждого обратимого технического шага. Статус `accepted` означает согласованный scope, не автоматически разрешённую публикацию.
4. **План.** Указать затронутые модули, порядок малых изменений, проверки и риски. Логика, данные и представление проверяются отдельно.
5. **Реализация.** Выполнить только scope; не исправлять весь backlog попутно. Regression-тесты для значимых ошибок и механик. Реализованный статус документа менять после проверки.
6. **Проверка.** Критерий → команда/сценарий → результат. Невыполненная проверка явно отмечается; запуск без исключения не подтверждает все игровые правила.
7. **Фиксация.** Обновить REQ/status, затронутую карту/архитектуру/README, ADR при значимом решении и `docs/updates/YYYY-MM-DD-slug.md`. В spec статус `implemented` либо `verified` по фактам.

## Статусы spec

`draft` → `accepted` → `implemented` → `verified`. `superseded` означает замену другой spec и содержит ссылку. В implemented код уже изменён, но часть критериев может не быть проверена. Verified означает, что все обязательные критерии пройдены, а ограничения перечислены. Исторические review/update не переписываются как будто старых дефектов не было.

Имена: `SPEC-001-short-topic.md`, следующие номера последовательны. Первый файл `_template.md` — шаблон, не утверждённая задача. ID требований сохраняются при правках, удалённое требование помечается заменённым со ссылкой.

## Хорошая постановка агенту

```text
Задача: исправить питание падальщика (REVIEW-01, REQ-FOOD-03).
Прочитай AGENTS.md и docs/architecture.md, проверь текущий код.
Критерии: живой субъект/тайл/удалённый труп не дают еду;
мёртвый существующий труп в зоне питания даёт +20 до max и расходуется один раз.
Scope: питание и безопасное удаление; навигацию и баланс не менять.
Добавь regression-проверки, выполни их и запиши update с результатами.
```

Если нужна навигация, добавить REQ-FOOD-04 отдельным scope или задачей. Для неизвестной механики формулировать открытые вопросы до реализации, а не просить агента «сделать красиво».

## Проверки

- **Чистая логика:** маленький мир, заданные компоненты, один ход/действие. Проверять ресурсы, цели, смерти, жизненный цикл, клонирование.
- **Интеграция:** загрузка всех JSON/PNG, создание default world, N ходов с seed, полный порядок фаз, queue/delete.
- **Интерфейс:** настоящее окно только для критериев, зависящих от изображения/раскладки/камеры или реального ввода. Смену источника данных HUD можно проверить без окна. Для логики приоритетны Python-тесты и текстовые снимки состояния; трассировка объясняет переходы, assertions проверяют результат.
- **Производительность:** отдельные turn/render timings, одинаковые размеры карты/популяции/seed, прогрев и число повторов. Не сравнивать разные режимы debug logging.

Пока нет pytest/CI и выделенного headless step. Не писать команды этих будущих инструментов как уже существующие. Regression-набор: `python -B -m unittest discover -s tests -v`. Текстовый сценарий падальщика: `python -B tests/trace_scavenger_search.py`. Настоящее окно с автоматическим HUD/выходом: `python -B tests/smoke_window.py`. Историческая диагностика: `python docs/reviews/reproduce_2026_10_11.py`; её exception entries — наблюдения, не авария runner, некоторые внутренние сигнатуры после исправлений изменились. Команды запуска приведены в README.

## Definition of Done

- Scope задачи выполнен; принятому поведению соответствуют код и данные.
- Все обязательные критерии имеют свидетельство проверки; отсутствующие проверки названы.
- При значимом баге/механике есть проверка наблюдаемого результата и границ, а не зеркальная копия реализации.
- Не изменён баланс/порядок/публичные имена вне scope; если изменён по задаче, это объяснено.
- Документы не заявляют несуществующих возможностей; добавлен update со ссылкой на spec/REQ/REVIEW.
- Diff проверен, чужие файлы не затёрты, временные артефакты не попали в продукт.

## Поддержание документации

После переименования модуля обновить project-map и ссылки. После изменения правила обновить project/requirements и критерии. После принятия альтернативы обновить ADR. В updates писать пользовательский эффект и проверки, а не только список файлов. Roadmap отражает оставшуюся работу; не отмечать этап завершённым после одной инфраструктурной функции.
